---
title:  'Building a Reproducible Validation Case'
---

A useful verification or validation case is small enough to understand, specific enough to reproduce, and explicit about what is being compared. The goal is not to create the largest possible test. The goal is to make one scientific claim that another contributor can check.

## First Decide What You Are Testing

**Verification** asks whether the software is solving the intended equations correctly. Typical references include analytic solutions, convergence studies, manufactured solutions, or trusted numerical benchmarks.

**Validation** asks whether the model agrees with physical or experimental reference data closely enough for the intended use. Typical references include wind-tunnel data, published measurements, or another documented physical dataset.

Keep that distinction in the write-up. A regression test can preserve either kind of result, but passing a regression test alone does not make a result physically validated.

## Minimum Useful Case

For a first contribution, prefer one case with:

- one geometry or configuration;
- one analysis setup;
- one reference dataset or published benchmark;
- a small number of comparison outputs;
- explicit units and coordinate conventions;
- a repeatable way to run the case;
- a clear pass/fail tolerance or an explicitly descriptive comparison if no tolerance has been accepted yet.

This is easier to review than a large campaign whose assumptions are difficult to isolate.

## Record the Inputs That Actually Matter

At minimum, capture:

| Category | Examples |
|:---------|:---------|
| Software | OpenVSP version or commit, VSPAERO solver version if relevant |
| Geometry | model file or script, reference dimensions, selected sets/surfaces |
| Flow/analysis | Mach, Reynolds number, angle of attack, wake settings, symmetry, method choices |
| Discretization | tessellation, paneling, mesh/refinement settings |
| Reference | source title, figure/table/case identifier, units, preprocessing steps |
| Comparison | output variables, normalization, sign convention, tolerance or error metric |

Do not rely on a screenshot to carry information that can be written down exactly.

## Keep the Case Reproducible from a Clean State

A reviewer should be able to understand how the result was produced without inheriting hidden state from your machine.

Good practice:

1. start from a known model or construct it in a script;
2. set important analysis inputs explicitly;
3. avoid depending on GUI state that the script does not recreate;
4. write outputs to predictable files or result objects;
5. document any external data that cannot live in the repository;
6. state any platform-specific requirements.

If a case only works after manually clicking several settings in the GUI, capture those settings in the script or document them precisely.

## Compare the Smallest Meaningful Set of Outputs

Choose outputs that directly support the claim. For aerodynamic work that might be a lift coefficient, drag coefficient, moment coefficient, pressure distribution, or a convergence trend.

Avoid validating dozens of outputs simply because they are available. Extra outputs increase review cost and can hide the one comparison that matters.

For each comparison, state:

- reference value or series;
- OpenVSP/VSPAERO value or series;
- units or nondimensionalization;
- absolute or relative difference;
- tolerance, if one is justified.

## Separate Reference Data from Generated Results

Treat source/reference data differently from outputs generated by the current code.

A good layout makes it obvious which files are:

- immutable source/reference data;
- scripts or configuration needed to reproduce the run;
- generated solver output;
- post-processing or comparison output.

Generated files should not become the source of truth merely because they were checked into a previous run.

## Use Existing Examples as Building Blocks, Not as Authority

Current examples and tests are useful for API syntax and analysis setup. Historical V&V drivers can also be useful for understanding older studies. Neither should replace the external reference for a validation claim.

When adapting an existing script:

- keep only the setup needed for the selected case;
- identify assumptions inherited from the example;
- update deprecated or superseded API usage;
- state what changed from the original example.

See [Scripting Examples: Where to Start](ScriptExamples.md) for guidance on choosing a source example.

## Suggested Review Checklist

Before proposing a new case, check that a reviewer can answer **yes** to each item:

- Is the purpose of the case stated in one or two sentences?
- Is the reference source unambiguous?
- Are the key input values explicit?
- Are coordinate systems and units clear?
- Can the run start from a clean checkout or documented model file?
- Are generated outputs separated from source/reference data?
- Are the comparison metrics easy to identify?
- Is the expected behavior or tolerance justified?
- Does the case avoid unrelated documentation or solver changes?

## What to Put in a Pull Request

A focused validation pull request should usually include:

1. **Reference** — exactly what published or trusted case is being reproduced.
2. **Setup** — geometry, analysis settings, and run instructions.
3. **Comparison** — the small set of outputs being checked.
4. **Result** — the observed agreement or discrepancy without overstating what it proves.
5. **Scope** — what the pull request intentionally does not attempt to validate.

If the result uncovers a discrepancy, that can still be a useful contribution. Preserve the reproducible case and describe the difference before changing solver behavior or reference data.
